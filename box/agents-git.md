## Git on this box (user rule 2026-10-25)
- Never commit or push to `main`/`master` (a pre-push hook blocks it). Start every task on a branch `box/<short-topic>` from an up-to-date `origin/main`.
- Sync first. At the start of every task, when you resume one, and before `gh pr create`, run `git fetch origin`. Branch from `origin/main` (`git switch -c box/<short-topic> origin/main`), never from a stale local `main`. If the current branch is behind `origin/main` (`git rev-list --count HEAD..origin/main` is not 0, or `behindDefault` in `~/.local/state/fcode/git-sync.json`), update it from `origin/main` before coding and re-run the tests: a branch that was never pushed is rebased (`git rebase origin/main`); a branch that is already on GitHub gets `git merge origin/main` (no rebase, no force-push); on `main` with no local changes use `git merge --ff-only origin/main`. The box timer (`fcode-git-sync`, every 5 minutes) fetches and reports in that file, and it may fast-forward a project's `main` (`git merge --ff-only`) when, at the moment it checks (right before the merge), the project is idle and clean: the checkout is on `main`, there are no tracked changes and no local commits, no merge / rebase / cherry-pick / revert / bisect is under way, no `filter.*` setting (Git LFS and the like) is configured anywhere on the box (a global `git lfs install` therefore switches this auto-update off for every project; agents' own sync covers that), the timer run is not already old, and no process of this user (an agent session, a shell, a tmux pane) has its working directory inside the work tree. An untracked or ignored file that the new commits would overwrite stops it. It never touches another branch, never stashes or resets, and never pushes. A session that starts a moment after that check can still see `main` move under it, and the timer can be minutes late, so every task still starts with its own sync as above. The `fcode-git-sync <project>` run before a new session only fetches and counts; it never moves the checkout. Never code on a stale main.
- Push the branch to `origin` as you go (it is the only backup: the box can pause or be deleted).
- A branch is done only after the reviewer PASS with test commands and exit codes (WORKFLOW rule 12). Then: `git fetch origin`, then bring the branch up to `origin/main` (`git rebase origin/main` if it was never pushed; `git merge origin/main` if it is already on GitHub; never force-push) and re-run the tests if anything changed, `gh pr create --base main --fill`, then wait for the PR's Actions runs to finish. The box token cannot read Checks, so `gh pr checks` fails with 403: list the runs with `gh run list --commit <sha>` (`<sha>` is the PR head: `gh pr view --json headRefOid -q .headRefOid`) and wait for each with `gh run watch <run-id> --exit-status`. Right after `gh pr create` the list can still be empty: poll `gh run list --commit <sha>` until at least one run is listed (up to about 5 minutes). If no run appears (the repo has no workflow for PRs), do NOT merge: give the user the PR link and say that there is no CI. Merge it yourself (user rule 2026-10-26) with `gh pr merge --squash --delete-branch` only when ALL of these hold: the reviewer PASS covers the final code, every Actions run for the PR head commit succeeded, the branch contains the current `origin/main` (rebased or merged as above), and the project's own release rules (its CLAUDE.md / AGENTS.md) allow a release right now. Then give the user the PR link and say what happens next.
- Release rules, per project. Before every merge, read the project's CLAUDE.md / AGENTS.md release and deploy rules; they win over this file. If a rule is unclear, or a time window cannot be checked, do not merge: give the user the PR link and say why.
  - vps-scraper (internal-scraper) uses SAFE-DEPLOY: a merge does not deploy; the deploy is only `scripts/deploy-safe.sh` on the VPS, followed by `scripts/data-continuity.sh`, run from the user's laptop. This box cannot reach the VPS. After the merge, tell the user: "đã merge, chờ safe-deploy từ laptop".
  - shopee-dashboard (repo VPS-Tracker): merging to `main` IS a production deploy (GitHub Actions, `.github/workflows/deploy.yml`). Merge only when its AGENTS.md allows a deploy (only between live sessions, never during one), and say so in the PR. After the merge, watch the deploy run (`gh run watch <id> --exit-status`) and report its result. On failure, tell the user at once and open a revert PR; do not merge the revert without the user.
  - deal-sync (repo BD-Team-Project): a merge does not deploy. The deploy is `scripts/deploy.sh` on the VPS, run from the user's laptop. After the merge, tell the user: "đã merge, chờ deploy từ laptop".
  - Any other project: follow its own deploy or release rule. If a merge would deploy and you cannot check that it is safe now, do not merge.
- Never touch the VPS directly.
- Never force-push, never rewrite `main` history, never merge a PR whose checks fail.
